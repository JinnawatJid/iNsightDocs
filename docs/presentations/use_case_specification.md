# Use Case Specification (Use Case Scheme)
เอกสารนี้อธิบายรายละเอียดการทำงาน (Specification) ของแต่ละ Use Case ในระบบ CreditInsight โดยอ้างอิงจาก Use Case Diagram และ Business Requirements (BR.txt)

---

## 1. ระบบย่อยที่ 1: ระบบจัดการสิทธิ์เข้าใช้งาน (Authentication & Authorization)
ระบบนี้รับผิดชอบกระบวนการยืนยันตัวตน (Authentication) ผ่าน SSO ขององค์กร และการจัดการสิทธิ์เข้าถึง (Authorization) ของผู้ใช้งาน โดยจะทำการตรวจสอบ Role เพื่อกำหนดสิทธิ์และขอบเขตการใช้งานเมนูต่างๆ ภายในแอปพลิเคชันอย่างถูกต้องและปลอดภัย

### **UC1.1: เข้าสู่ระบบ (Login)**
* **Actor:** ผู้ใช้งานทุกบทบาท (ผู้จัดการสาขา, ผู้จัดการภูมิภาค, ผู้จัดการฝ่ายขาย, เจ้าหน้าที่การเงิน, ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต, ผู้ดูแลระบบ)
* **Description:** ผู้ใช้งานเข้าสู่ระบบเพื่อใช้งานแอปพลิเคชัน CreditInsight ผ่านระบบ Single Sign-On (SSO) ขององค์กร
* **Pre-conditions:** ผู้ใช้งานต้องมีบัญชีขององค์กร (SSO)
* **Post-conditions:** ระบบได้รับ JWT Token จากระบบ SSO ภายนอก และถอดรหัส (Decode) ข้อมูลเพื่อใช้ยืนยันสิทธิ์ในการเข้าใช้งานแอปพลิเคชัน
* **Main Flow:**
  1. ผู้ใช้งานเปิดหน้าเว็บแอปพลิเคชัน CreditInsight
  2. ระบบ (Frontend Router) ตรวจสอบสถานะการเข้าสู่ระบบ (Token/Session) ในเครื่องปัจจุบัน
  3. กรณีไม่พบ Token ระบบจะนำทาง (Redirect) ผู้ใช้งานไปยังหน้าจอ Login ของ **ระบบ SSO ขององค์กร** อัตโนมัติ (`<<includes>>`)
  4. ผู้ใช้งานกรอกข้อมูลประจำตัว (รหัสพนักงานและรหัสผ่าน) บนหน้าจอของ SSO
  5. ระบบ SSO ยืนยันตัวตนสำเร็จ และนำทางกลับมายังแอปพลิเคชัน (Callback) พร้อมแนบ JWT Token
* **Alternate Flow:**
  * 2a. หากพบ Token ที่ยังไม่หมดอายุในเครื่อง: ระบบจะข้ามขั้นตอน SSO และเข้าสู่แอปพลิเคชันได้ทันที
  * 4a. หากรหัสพนักงานหรือรหัสผ่านผิด: ระบบ SSO ภายนอกจะดำเนินการแจ้งเตือนผู้ใช้เองตามมาตรฐานขององค์กร
  * 5a. หาก Token ที่ได้รับมาหมดอายุหรือไม่ถูกต้อง: ระบบหลังบ้าน (Backend) จะปฏิเสธการเชื่อมต่อและแสดงข้อความแจ้งเตือน "Authentication failed"

### **UC1.2: ตรวจสอบสิทธิ์และแสดงเมนูตามบทบาท (Authorize & Render Menu)**
* **Actor:** ระบบ (System) / ผู้ใช้งานทุกบทบาท
* **Description:** ระบบตรวจสอบบทบาท (Role) ของผู้ใช้งานจากข้อมูลที่ผูกไว้ เพื่อแสดงผลหน้าจอและเมนูการใช้งานให้สอดคล้องกับสิทธิ์
* **Pre-conditions:** ผู้ใช้งานผ่านการยืนยันตัวตน (Login สำเร็จ)
* **Post-conditions:** ระบบแสดง Dashboard และเมนูที่ตรงกับ Role ของผู้ใช้งาน
* **Main Flow:**
  1. ระบบดึงข้อมูลบทบาท (Role) จากโครงสร้างข้อมูลภายใน JWT (JSON Web Token) ที่ได้รับมา
  2. ระบบตรวจสอบเงื่อนไขสิทธิ์ผ่าน Dynamic RBAC Matrix
  3. ระบบนำทาง (Redirect) ผู้ใช้งานไปยังหน้าแรกที่กำหนดไว้ตามบทบาท
  4. ระบบแสดงเมนูบนแถบนำทางด้านบน (Navbar) เท่าที่ผู้ใช้งานรายนั้นมีสิทธิ์เข้าถึง (เช่น ผู้ดูแลระบบเห็นเมนู "ตั้งค่าระบบ")

## 2. ระบบย่อยที่ 2: ระบบสร้างและจัดการคำขอ (Request Creation & Management)
ระบบนี้ให้ผู้จัดการสาขาใช้สำหรับค้นหาข้อมูลลูกค้าและสร้างคำขอเครดิตใหม่ โดยครอบคลุมตั้งแต่การกรอกข้อมูล แนบไฟล์เอกสาร บันทึกร่างแบบฟอร์ม ตรวจสอบความถูกต้อง ไปจนถึงการส่งคำขอซึ่งจะกระตุ้นการประเมินคะแนนความเสี่ยง (Scoring) อัตโนมัติ

### **UC2.1: ค้นหาและตรวจสอบสถานะลูกค้า (Search Customer)**
* **Actor:** ผู้จัดการสาขา
* **Description:** ผู้จัดการสาขาค้นหาข้อมูลลูกค้าจากฐานข้อมูลกลางเพื่อตรวจสอบสถานะก่อนเริ่มสร้างคำขอเครดิต
* **Pre-conditions:** ผู้จัดการสาขาเข้าสู่ระบบเรียบร้อยแล้ว
* **Post-conditions:** ระบบแสดงข้อมูลลูกค้า สถานะ NPL/Blacklist และประวัติการซื้อ
* **Main Flow:**
  1. ผู้จัดการสาขาเข้าสู่หน้าจอ "ค้นหาลูกค้า"
  2. ผู้จัดการสาขากรอกคำค้นหา เช่น รหัสลูกค้า, ชื่อ, เบอร์โทร หรือ เลขประจำตัวผู้เสียภาษี
  3. ระบบค้นหาข้อมูลจากฐานข้อมูลส่วนกลาง (ผ่าน API ของระบบ UXP หรือฐานข้อมูลในระบบ CreditInsight)
  4. ระบบแสดงข้อมูลรายละเอียดลูกค้า
  5. ระบบทำการ `<<includes>>` **UC2.2 ดึงประวัติการซื้อย้อนหลัง 3 เดือน** อัตโนมัติ
* **Alternate Flow:**
  * 3a. ไม่พบข้อมูลลูกค้า: ระบบแสดงปุ่มให้ "เพิ่มข้อมูลลูกค้าใหม่"

### **UC2.2: ดึงประวัติการซื้อย้อนหลัง 3 เดือน (Fetch UXP History)**
* **Actor:** ระบบ (System)
* **Description:** ระบบดึงข้อมูลประวัติการทำธุรกรรม (ยอดซื้อและยอดชำระ) ย้อนหลัง 3 เดือนจากระบบ UXP เพื่อมาแสดงให้ผู้จัดการสาขาทราบ
* **Pre-conditions:** มีการค้นหาลูกค้าและพบข้อมูลรหัสลูกค้า
* **Post-conditions:** ข้อมูลประวัติการซื้อถูกนำมาแสดงผลบนหน้าจอค้นหา
* **Main Flow:**
  1. ระบบส่ง API Request ไปยัง **ระบบ UXP** พร้อมกับรหัสลูกค้า
  2. ระบบ UXP ตอบกลับข้อมูลรายการ Invoice และการชำระเงินย้อนหลัง 3 เดือน
  3. ระบบนำข้อมูลมาแสดงผลในตารางประวัติการซื้อ

### **UC2.3: สร้างคำขอเครดิต (Create Credit Request)**
* **Actor:** ผู้จัดการสาขา
* **Description:** ผู้จัดการสาขากรอกข้อมูลรายละเอียดคำขอเครดิต เช่น วงเงินที่ต้องการ ระยะเวลาชำระหนี้ และข้อมูลทางบัญชี
* **Pre-conditions:** ผ่านการค้นหาลูกค้าแล้ว และลูกค้าไม่ติด Blacklist หรือ NPL (เว้นแต่ได้รับอนุมัติพิเศษ)
* **Post-conditions:** ข้อมูลคำขอเครดิตถูกเตรียมพร้อมสำหรับส่ง หรือถูกบันทึกเป็นร่าง
* **Main Flow:**
  1. ผู้จัดการสาขากดปุ่ม "สร้างคำขอเครดิต" จากหน้าโปรไฟล์ลูกค้า
  2. ระบบแสดงฟอร์มสร้างคำขอเครดิต
  3. ผู้จัดการสาขากรอกข้อมูลวงเงินที่ขอ เงื่อนไขการชำระ และกรอกข้อมูลงบการเงิน
  4. ผู้จัดการสาขาต้องทำ **UC2.4 แนบไฟล์เอกสาร** (`<<includes>>`) เพื่อประกอบคำขอ
  5. ผู้จัดการสาขาตรวจสอบข้อมูลและดำเนินการขั้นต่อไป
* **Alternate Flow:**
  * 3a. ผู้จัดการสาขาสามารถเลือกทำ **UC2.5 บันทึกฉบับร่าง** (`<<extends>>`) เพื่อเก็บข้อมูลไว้กรอกต่อในภายหลังได้

### **UC2.4: แนบไฟล์เอกสาร (Attach Documents)**
* **Actor:** ผู้จัดการสาขา
* **Description:** ผู้จัดการสาขาทำการอัปโหลดไฟล์เอกสารประกอบ เช่น งบการเงินจาก DBD หรือ สเตทเม้นท์ธนาคาร
* **Pre-conditions:** อยู่ในหน้าฟอร์มสร้างคำขอเครดิต
* **Post-conditions:** ไฟล์เอกสารอัปโหลดสำเร็จและผูกติดกับคำขอเครดิต
* **Main Flow:**
  1. ผู้จัดการสาขาคลิกที่กล่องอัปโหลด (Upload Box) ในหัวข้อเอกสารที่ต้องการ
  2. ผู้จัดการสาขาเลือกไฟล์เอกสาร (เช่น PDF, Excel) จากเครื่องคอมพิวเตอร์
  3. ระบบตรวจสอบขนาดและประเภทไฟล์ (ไม่เกิน 20MB)
  4. ระบบอัปโหลดไฟล์ไปเก็บในเซิร์ฟเวอร์
  5. ระบบแสดงรายการไฟล์ที่แนบสำเร็จบนหน้าจอ

### **UC2.5: บันทึกฉบับร่าง (Save Draft)**
* **Actor:** ผู้จัดการสาขา
* **Description:** ผู้จัดการสาขาบันทึกข้อมูลที่กรอกค้างไว้โดยที่ยังไม่ส่งเข้ากระบวนการอนุมัติ
* **Pre-conditions:** มีการกรอกข้อมูลในฟอร์มสร้างคำขอบางส่วนแล้ว
* **Post-conditions:** ข้อมูลคำขอถูกบันทึกในสถานะ "Draft" (ฉบับร่าง)
* **Main Flow:**
  1. ผู้จัดการสาขากดปุ่ม "บันทึกร่าง"
  2. ระบบบันทึกข้อมูลแบบชั่วคราว (Snapshot) ลงฐานข้อมูล
  3. ระบบแจ้งเตือน "บันทึกฉบับร่างสำเร็จ" และนำผู้ใช้งานกลับไปที่รายการคำขอ

### **UC2.6: ส่งคำขอเครดิต (Submit Request)**
* **Actor:** ผู้จัดการสาขา
* **Description:** ผู้จัดการสาขากดส่งคำขอเข้าสู่กระบวนการพิจารณาอนุมัติ
* **Pre-conditions:** ข้อมูลบังคับในฟอร์มถูกกรอกครบถ้วนและแนบเอกสารสำคัญแล้ว
* **Post-conditions:** คำขอเครดิตเปลี่ยนสถานะเป็น "Opened (รอดำเนินการ)" และถูกส่งเข้า Workflow
* **Main Flow:**
  1. ผู้จัดการสาขากดปุ่ม "ส่งคำขอ"
  2. ระบบทำ **UC2.7 ตรวจสอบความครบถ้วน** (`<<includes>>`)
  3. ระบบทำ **UC2.8 คำนวณคะแนนความเสี่ยง** (`<<includes>>`)
  4. ระบบสร้างรายการแจ้งเตือนไปยังผู้มีหน้าที่รับผิดชอบในลำดับถัดไป

### **UC2.7: ตรวจสอบความครบถ้วน (Validate Form Completeness)**
* **Actor:** ระบบ (System)
* **Description:** ระบบรันโปรแกรมตรวจสอบว่าฟิลด์ข้อมูลที่บังคับกรอก (Mandatory Fields) ได้รับการเติมเต็มหรือไม่
* **Pre-conditions:** มีการกดปุ่ม "ส่งคำขอ"
* **Post-conditions:** ฟอร์มผ่านการ Validate
* **Main Flow:**
  1. ระบบวนลูปตรวจสอบค่าในฟอร์มตามกฎของประเภทคำขอนั้นๆ
  2. หากครบถ้วน ให้ดำเนินการขั้นตอนต่อไป
* **Alternate Flow:**
  * 2a. ข้อมูลไม่ครบ: ระบบระงับการส่ง และ Highlight ฟิลด์สีแดงพร้อมแสดงข้อความเตือนให้ผู้ใช้งานแก้ไข

### **UC2.8: คำนวณคะแนนความเสี่ยง Scoring Engine (Calculate Risk Score)**
* **Actor:** ระบบ (System)
* **Description:** ระบบนำข้อมูลการเงินและพฤติกรรมลูกค้ามาคำนวณผ่านโมเดลคะแนน (Scorecard) เพื่อหา Grade และวงเงินแนะนำ
* **Pre-conditions:** ฟอร์มผ่านการตรวจสอบความครบถ้วน (UC2.7) สำเร็จ
* **Post-conditions:** คำขอเครดิตถูกประทับด้วยคะแนน (Score), เกรด (Grade) และวงเงินแนะนำ (Recommended Limit) ในฐานข้อมูล (Snapshot Data)
* **Main Flow:**
  1. ระบบดึงเงื่อนไข Scorecard จากฐานข้อมูล (JSON Config)
  2. ระบบนำข้อมูลในฟอร์มแมปเข้ากับโมเดลการให้คะแนน
  3. ระบบคำนวณผลรวมคะแนนและกำหนดระดับความเสี่ยง
  4. ระบบคำนวณ "วงเงินที่แนะนำ" ด้วยสูตรทางคณิตศาสตร์

## 3. ระบบย่อยที่ 3: ระบบตรวจสอบและส่งต่อ (Review & Forward Process)
ระบบนี้เป็นพื้นที่สำหรับผู้ตรวจสอบ (เช่น ผู้จัดการภูมิภาค, ฝ่ายขาย, ฝ่ายการเงิน) ในการเข้ามาพิจารณากลั่นกรองคำขอเครดิต โดยสามารถดูรายละเอียด เอกสารแนบ เพิ่มข้อคิดเห็น และส่งต่อคำขอไปยังลำดับถัดไปใน Workflow

### **UC3.1: ดูรายการเอกสารรอตรวจสอบ (View Pending Reviews)**
* **Actor:** ผู้ตรวจสอบ (ผู้จัดการภูมิภาค, ผู้จัดการฝ่ายขาย, เจ้าหน้าที่การเงิน)
* **Description:** ผู้ตรวจสอบเข้ามาดูรายการคำขอเครดิตที่รอให้ตนเองดำเนินการพิจารณากลั่นกรอง
* **Pre-conditions:** ผู้ตรวจสอบเข้าสู่ระบบและมีสิทธิ์ใน Workflow ขั้นตอนปัจจุบัน
* **Post-conditions:** ระบบแสดงรายการคำขอเครดิตพร้อมสถานะปัจจุบัน
* **Main Flow:**
  1. ผู้ตรวจสอบกดเข้าเมนู "คำขอทั้งหมด" (Pending Requests)
  2. ระบบคิวรีฐานข้อมูลโดยกรองเฉพาะคำขอที่อยู่ในสถานะและพื้นที่ความรับผิดชอบของผู้ตรวจสอบ
  3. ระบบแสดงข้อมูลในรูปแบบตารางสรุป

### **UC3.2: เปิดอ่านคำขอและดาวน์โหลดไฟล์แนบ (Read Request & Download Attachments)**
* **Actor:** ผู้ตรวจสอบ (ผู้จัดการภูมิภาค, ผู้จัดการฝ่ายขาย, เจ้าหน้าที่การเงิน)
* **Description:** ผู้ตรวจสอบคลิกเพื่อดูรายละเอียดเชิงลึกของคำขอและดาวน์โหลดเอกสารประกอบ
* **Pre-conditions:** อยู่หน้าจอคำขอทั้งหมด
* **Post-conditions:** ผู้ตรวจสอบได้รับข้อมูลครบถ้วนสำหรับประกอบการพิจารณา
* **Main Flow:**
  1. ผู้ตรวจสอบคลิกที่รายการคำขอที่ต้องการ
  2. ระบบแสดงหน้าจอ Review Dashboard พร้อมข้อมูลลูกค้า ข้อมูลการขอ และประวัติ
  3. ผู้ตรวจสอบคลิกที่รายชื่อไฟล์เอกสารแนบ
  4. ระบบทำการส่งไฟล์หรือเปิดไฟล์ผ่าน Image Viewer เพื่อให้ผู้ตรวจสอบดูรายละเอียด

### **UC3.3: ให้ความคิดเห็นและส่งต่อ (Review and Forward)**
* **Actor:** ผู้ตรวจสอบ (ผู้จัดการภูมิภาค, ผู้จัดการฝ่ายขาย, เจ้าหน้าที่การเงิน)
* **Description:** ผู้ตรวจสอบพิมพ์ความคิดเห็น (Comment) และกดดำเนินการเพื่อส่งเรื่องไปยังขั้นตอนถัดไป
* **Pre-conditions:** ผู้ตรวจสอบกำลังเปิดอ่านคำขออยู่
* **Post-conditions:** คำขอถูกเปลี่ยนสถานะเป็นขั้นถัดไปและมีบันทึก Audit Trail ของผู้ตรวจสอบ
* **Main Flow:**
  1. ผู้ตรวจสอบพิมพ์ข้อความลงในช่องความเห็น
  2. ผู้ตรวจสอบกดปุ่ม "ให้ความคิดเห็น" หรือ "ส่งต่อ" (Approve/Forward ในบริบทของ Reviewer)
  3. ระบบบันทึกข้อความเห็นลงฐานข้อมูล
  4. ระบบเปลี่ยนสถานะ Workflow (เช่น จาก Opened รอดำเนินการ -> RegionalSubmitted ผ่านการพิจารณาพื้นที่)
  5. ระบบทำการ `<<includes>>` **UC3.4 แจ้งเตือนไปยังผู้รับผิดชอบลำดับถัดไป**

### **UC3.4: แจ้งเตือนไปยังผู้รับผิดชอบลำดับถัดไป (Notify Next Role)**
* **Actor:** ระบบ (System)
* **Description:** ระบบส่งการแจ้งเตือนไปยัง Role ถัดไปใน Workflow อัตโนมัติเมื่อสถานะคำขอเปลี่ยน
* **Pre-conditions:** การเปลี่ยนสถานะ Workflow สำเร็จ (เช่น UC3.3 ทำงานเสร็จ)
* **Post-conditions:** ผู้มีหน้าที่ถัดไปได้รับแจ้งเตือน (Notification) บนหน้าจอของตนเอง
* **Main Flow:**
  1. ระบบตรวจสอบการตั้งค่า Workflow (WORKFLOW_CONFIG) ว่าสถานะปัจจุบันใครเป็นผู้รับผิดชอบ
  2. ระบบสร้าง Notification Record ลงในตาราง `Notifications` ในฐานข้อมูล โดยผูกกับ `target_role` หรือ `target_username` เพื่อให้ระบบหน้าบ้านนำไปแสดงผล
  3. ผู้รับผิดชอบเห็นแจ้งเตือนแสดงขึ้นบน Notification Bell ในแอปพลิเคชัน

## 4. ระบบย่อยที่ 4: ระบบพิจารณาอนุมัติ (Approval Process)
ระบบนี้รองรับกระบวนการตัดสินใจขั้นสุดท้ายโดยผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน หรือ คณะกรรมการเครดิต) ซึ่งสามารถตรวจสอบข้อมูลทั้งหมด รวมถึงคะแนนความเสี่ยง เพื่อพิจารณาอนุมัติตามคำขอ ปรับลดวงเงิน/เงื่อนไข หรือปฏิเสธคำขอ พร้อมแจ้งเตือนผลกลับไปยังสาขา

### **UC4.1: ดูรายการเอกสารรออนุมัติ (View Pending Approvals)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติเปิดดูรายการคำขอเครดิตที่ผ่านการกลั่นกรองและรอการตัดสินใจขั้นตอนสุดท้าย
* **Pre-conditions:** เข้าสู่ระบบและมีบทบาทเป็นผู้อนุมัติ
* **Post-conditions:** ระบบแสดงรายการคำขอที่รออนุมัติพร้อมยอดเงินรวมเบื้องต้น
* **Main Flow:**
  1. ผู้อนุมัติกดเข้าเมนู "คำขอทั้งหมด" (Pending Requests)
  2. ระบบแสดงตารางรายการคำขอเรียงตามวันที่สร้าง

### **UC4.2: เปิดอ่านคำขอและดาวน์โหลดไฟล์แนบ (Read & Verify Request)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติเปิดดูรายละเอียดคำขอ ตรวจสอบเอกสาร และตรวจสอบวงเงินแนะนำจากระบบก่อนตัดสินใจ
* **Pre-conditions:** คลิกเลือกรายการจากหน้าคำขอทั้งหมด
* **Post-conditions:** ผู้อนุมัติได้พิจารณาข้อมูลรวมถึงคะแนนความเสี่ยง
* **Main Flow:**
  1. ผู้อนุมัติคลิกเปิดคำขอ
  2. ระบบแสดงหน้าจอพิจารณาคำขอ (Review Dashboard)
  3. ผู้อนุมัติดาวน์โหลดและตรวจสอบไฟล์
  4. ผู้อนุมัติต้องทำ **UC4.3 ตรวจสอบวงเงินแนะนำจากระบบ** (`<<includes>>`) บนหน้าจอ Review Dashboard ก่อนดำเนินการต่อ

### **UC4.3: ตรวจสอบวงเงินแนะนำจากระบบ (Verify Recommended Limit)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติต้องอ่านและอ้างอิงข้อมูล "วงเงินแนะนำ" (Recommended Limit) ที่ระบบคำนวณไว้เป็นหลักเกณฑ์ประกอบการตัดสินใจ
* **Pre-conditions:** ผู้อนุมัติเปิดอ่านรายละเอียดคำขอบนหน้าจอ Review Dashboard เรียบร้อยแล้ว
* **Post-conditions:** ผู้อนุมัติรับทราบวงเงินแนะนำและเงื่อนไข Scoring
* **Main Flow:**
  1. ระบบแสดงหน้าต่าง หรือ Card แจ้ง "ผลการพิจารณาจากระบบ (System Recommendation)"
  2. ผู้อนุมัติอ่านค่าคะแนนรวม เกรด และวงเงินแนะนำที่ระบบแสดงไว้เด่นชัดบนหน้าจอ

### **UC4.4: อนุมัติวงเงินตามขอ (Approve as Requested)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติเห็นด้วยกับวงเงินและเงื่อนไขที่สาขาร้องขอมาทั้งหมด
* **Pre-conditions:** ผู้อนุมัติเปิดอ่านคำขอ และยอดวงเงินไม่เกินสิทธิ์ของผู้อนุมัติรายนั้น (ผจก.การเงิน <= 300k, กรรมการ > 300k)
* **Post-conditions:** คำขอสิ้นสุดกระบวนการ สถานะเปลี่ยนเป็น "อนุมัติ"
* **Main Flow:**
  1. ผู้อนุมัติใส่ข้อความเห็น และไม่แก้ไขตัวเลขวงเงินใดๆ
  2. ผู้อนุมัติกดปุ่ม "อนุมัติ (Approve)"
  3. ระบบเปลี่ยนสถานะคำขอเป็น Final Approved พร้อมบันทึก Audit Trail
  4. ระบบทำ **UC4.7 แจ้งเตือนผลกลับไปยังผู้สร้างคำขอ** (`<<includes>>`)

### **UC4.5: ปรับแก้ไขมูลค่าวงเงินใหม่ (Adjust Limit and Approve)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติเห็นสมควรอนุมัติเครดิต แต่ต้องการปรับลดยอดเงิน หรือปรับเปลี่ยนเงื่อนไขการชำระเงินใหม่
* **Pre-conditions:** ผู้อนุมัติเปิดอ่านคำขอ และพิจารณาว่ามีความเสี่ยง จึงปรับลดตัวเลข
* **Post-conditions:** คำขออนุมัติด้วยเงื่อนไขใหม่
* **Main Flow:**
  1. ผู้อนุมัติกรอกตัวเลขวงเงินที่อนุมัติจริงทับลงในช่องข้อมูล
  2. ผู้อนุมัติใส่ข้อความเห็น
  3. ผู้อนุมัติกดปุ่ม "อนุมัติ (Approve)"
  4. ระบบบันทึกเงื่อนไขใหม่ทับข้อมูลเดิม พร้อมแนบประวัติ Audit Trail ว่ามีการเปลี่ยนแปลงจากตัวเลขเดิมเท่าไหร่
  5. ระบบเปลี่ยนสถานะเป็น Final Approved
  6. ระบบทำ **UC4.7 แจ้งเตือนผลกลับไปยังผู้สร้างคำขอ** (`<<includes>>`)

### **UC4.6: ปฏิเสธคำขอ (Reject Request)**
* **Actor:** ผู้อนุมัติ (ผู้จัดการฝ่ายการเงิน, คณะกรรมการเครดิต)
* **Description:** ผู้อนุมัติพิจารณาแล้วเห็นว่าลูกค้ามีความเสี่ยงสูงมาก จึงตัดสินใจไม่อนุมัติเครดิต
* **Pre-conditions:** ผู้อนุมัติพิจารณาข้อมูลและพบเหตุผลที่ไม่สามารถให้เครดิตได้
* **Post-conditions:** คำขอเปลี่ยนสถานะเป็น "ปฏิเสธ (Rejected)"
* **Main Flow:**
  1. ผู้อนุมัติกรอกเหตุผลที่ปฏิเสธในช่องความคิดเห็น (บังคับ)
  2. ผู้อนุมัติกดปุ่ม "ปฏิเสธ (Reject)"
  3. ระบบเปลี่ยนสถานะคำขอเป็น Rejected
  4. ระบบทำ **UC4.7 แจ้งเตือนผลกลับไปยังผู้สร้างคำขอ** (`<<includes>>`)

### **UC4.7: แจ้งเตือนผลกลับไปยังผู้สร้างคำขอ (Notify Result to Creator)**
* **Actor:** ระบบ (System)
* **Description:** ระบบส่งการแจ้งเตือนผลลัพธ์สุดท้าย (อนุมัติ หรือ ปฏิเสธ) ให้ผู้จัดการสาขาทราบโดยตรง
* **Pre-conditions:** กระบวนการพิจารณาของผู้อนุมัติเสร็จสิ้น (เกิดจาก UC4.4, 4.5, หรือ 4.6)
* **Post-conditions:** ผู้จัดการสาขาได้รับ Notification บนหน้าจอของตน
* **Main Flow:**
  1. ระบบตรวจสอบรหัสผู้ใช้งานผู้สร้างคำขอ (Initiator) จากคอลัมน์ `created_by` ในตาราง `CreditRequests`
  2. ระบบสร้าง Notification Record แจ้งผลการตัดสินลงในตาราง `Notifications` โดยกำหนด `target_username` ให้ตรงกับผู้สร้างคำขอคนนั้น

## 5. ระบบย่อยที่ 5: ระบบตั้งค่า (System Configuration)
ระบบนี้เป็นศูนย์กลางสำหรับผู้ดูแลระบบ (Admin) ในการตั้งค่าพารามิเตอร์การทำงานของระบบ จัดการสิทธิ์ผู้ใช้งาน (RBAC) กำหนดผังความรับผิดชอบพื้นที่/สาขา และปรับปรุงเกณฑ์การให้คะแนนความเสี่ยง (Scorecards) เพื่อให้ระบบสอดคล้องกับนโยบายขององค์กร

### **UC5.1: จัดการการตั้งค่าระบบทั่วไป (Manage System Rules)**
* **Actor:** ผู้ดูแลระบบ (Admin)
* **Description:** ผู้ดูแลระบบทำการปรับเปลี่ยนพารามิเตอร์การทำงานพื้นฐานของระบบ เช่น อายุไฟล์ข้อมูล (Freshness days) ขีดจำกัดการแนบไฟล์ เป็นต้น
* **Pre-conditions:** ผู้ใช้เข้าสู่ระบบด้วยสิทธิ์ "ผู้ดูแลระบบ" และเปิดเข้าเมนู "ตั้งค่าระบบ"
* **Post-conditions:** ค่าพารามิเตอร์ระบบถูกปรับเปลี่ยนและมีผลบังคับใช้ในระบบทันที
* **Main Flow:**
  1. ผู้ดูแลระบบเข้าหน้า "ตั้งค่าระบบ" และเลือกแท็บ "การตั้งค่าระบบ"
  2. ระบบแสดงรายการพารามิเตอร์พร้อมค่าปัจจุบัน
  3. ผู้ดูแลระบบแก้ไขตัวเลขหรือเปิด/ปิดฟังก์ชันการทำงาน
  4. ผู้ดูแลระบบกดบันทึก
  5. ระบบบันทึกข้อมูลทับในฐานข้อมูล `Configurations` และแสดงข้อความสำเร็จ

### **UC5.2: จัดการสิทธิ์ผู้ใช้งาน (Manage User Roles)**
* **Actor:** ผู้ดูแลระบบ (Admin)
* **Description:** ผู้ดูแลระบบทำการผูกกลุ่มผู้ใช้จาก SSO (Role Mapping) เข้ากับสิทธิ์ (Permissions) ภายในระบบผ่าน Dynamic RBAC Matrix
* **Pre-conditions:** อยู่ในหน้าตั้งค่าระบบ
* **Post-conditions:** สิทธิ์การเข้าถึงเมนูและฟังก์ชันต่างๆ ของ Role ถูกปรับปรุง
* **Main Flow:**
  1. ผู้ดูแลระบบเข้าแท็บ "จัดการสิทธิ์ผู้ใช้งาน"
  2. ระบบแสดงตาราง Matrix สิทธิ์การเข้าใช้งาน
  3. ผู้ดูแลระบบปรับเปลี่ยน Checkbox เพื่อให้/ริบสิทธิ์เมนูและฟังก์ชันการทำงานต่างๆ ของแต่ละบทบาท
  4. ผู้ดูแลระบบกดบันทึก

### **UC5.3: จัดการพื้นที่และสาขา (Manage Region Mapping)**
* **Actor:** ผู้ดูแลระบบ (Admin)
* **Description:** ผู้ดูแลระบบตั้งค่าการจัดกลุ่มรหัสสาขาให้เข้าไปอยู่ใน "ภูมิภาค" หรือ "พื้นที่" เพื่อให้ผู้จัดการภูมิภาค/ภาค สามารถมองเห็นข้อมูลคำขอของสาขาลูกข่ายตนเองได้
* **Pre-conditions:** อยู่ในหน้าตั้งค่าระบบ
* **Post-conditions:** โครงสร้างการมองเห็นข้อมูลตามพื้นที่ (Data Visibility) ถูกอัปเดต
* **Main Flow:**
  1. ผู้ดูแลระบบเข้าแท็บ "จัดการพื้นที่และสาขา"
  2. ระบบแสดงรายการภูมิภาค และรหัสสาขา (Branch Codes) ที่ผูกอยู่
  3. ผู้ดูแลระบบสามารถเพิ่มรหัสสาขาใหม่เข้าไปในภูมิภาค หรือย้ายสาขา
  4. ผู้ดูแลระบบกดบันทึก ระบบบันทึกข้อมูล JSON ลงฐานข้อมูล

### **UC5.4: จัดการโมเดลให้คะแนน (Manage Scorecards)**
* **Actor:** ผู้ดูแลระบบ (Admin)
* **Description:** ผู้ดูแลระบบปรับปรุงน้ำหนักคะแนน (Weights), ตัวแปร (Factors), และเกณฑ์ขั้นต่ำ/สูงสุด ที่ใช้ในระบบ Scoring Engine
* **Pre-conditions:** อยู่ในหน้าตั้งค่าระบบ
* **Post-conditions:** ระบบ Scoring คำนวณความเสี่ยงด้วยเกณฑ์ใหม่สำหรับคำขอที่จะสร้างขึ้นในอนาคต
* **Main Flow:**
  1. ผู้ดูแลระบบเข้าแท็บ "โมเดลให้คะแนน"
  2. ระบบแสดงตารางปัจจัยชี้วัดและคะแนนที่ให้ในแต่ละช่วงเกณฑ์
  3. ผู้ดูแลระบบแก้ไขค่าน้ำหนักคะแนนให้ตรงตามนโยบายสินเชื่อใหม่
  4. ผู้ดูแลระบบกดบันทึก ระบบบันทึก JSON การคำนวณใหม่ลงฐานข้อมูล
