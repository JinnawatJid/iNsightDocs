# คำอธิบายโครงสร้างฐานข้อมูล (ER Diagram) ของระบบแนะนำวงเงินเครดิต

แผนภาพ ER Diagram (อ้างอิงจากรูปที่ 3.9) แสดงการออกแบบโครงสร้างฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ของโปรแกรมแนะนำวงเงินเครดิตสำหรับลูกค้า เพื่อรองรับกระบวนการขออนุมัติสินเชื่อแบบอัตโนมัติและกึ่งอัตโนมัติ โดยมีศูนย์กลางอยู่ที่ตารางคำขอเครดิต (Credit Requests) ซึ่งเชื่อมโยงกับข้อมูลลูกค้าและระบบสนับสนุนการทำงานอื่นๆ โดยสามารถอธิบายภาพรวมของเอนทิตี (Entity) ทั้ง 6 ตัว และความสัมพันธ์ (Relationships) โดยอ้างอิงจากโครงสร้างจริงของระบบโค้ด (เช่นใน `db-sqlite.js` และ `db-mssql.js`) ดังนี้:

### 1. เอนทิตี Customers (ข้อมูลลูกค้าหลัก)
*   **บริบททางธุรกิจ (Business Context):** เป็นข้อมูลหลักของลูกค้า (Master Data) ที่เชื่อมโยงกับระบบ Enterprise ภายนอก (เช่น ระบบ UXP/ERP) โดยระบบ CreditInsight จะทำการดึงและซิงโครไนซ์ข้อมูลเหล่านี้มาจากไฟล์ CSV (เช่น `Customers_rows.csv`) แบบอัตโนมัติ เพื่อนำข้อมูลประวัติมาใช้ประกอบการพิจารณาความเสี่ยง
*   **โครงสร้าง (Attributes):** มี Primary Key คือ `No_` (รหัสลูกค้า) และจัดเก็บข้อมูลสำคัญ เช่น `Name` (ชื่อลูกค้า), `Address` (ที่อยู่), `Phone_No_` (เบอร์โทรศัพท์), `Credit_Limit_LCY` (วงเงินเครดิตเดิม) และ `Payment_Terms_Code` (เงื่อนไขการชำระเงินเดิม)
*   **ความสัมพันธ์ (Relationship):** มีความสัมพันธ์แบบ One-to-Many (1:M) กับเอนทิตี `CreditRequests` เนื่องจากลูกค้า 1 รายสามารถสร้างคำขอพิจารณาวงเงินเครดิตใหม่ได้หลายครั้ง และสัมพันธ์แบบ One-to-One (1:1) กับ `CustomerBlacklist` ผ่านเลขประจำตัวผู้เสียภาษี

### 2. เอนทิตี CustomerBlacklist (ข้อมูลบัญชีดำของลูกค้า)
*   **บริบททางธุรกิจ:** เป็นข้อมูลบัญชีดำ (NPL / Blacklist) ที่มีการจัดการผ่านไฟล์ `CustomerBlacklist_rows.csv` เพื่อใช้เป็นมาตรการป้องกันความเสี่ยง (Risk Management) ระบบจะตรวจสอบเลขที่บัตรประชาชนหรือรหัสผู้เสียภาษี หากพบว่าลูกค้าติดประวัติบังคับคดี หรือยึดทรัพย์ ระบบจะแจ้งเตือนให้ผู้พิจารณาทราบทันที
*   **โครงสร้าง (Attributes):** จัดเก็บข้อมูลหลักได้แก่ `tax_id` (เลขประจำตัวประชาชน/ผู้เสียภาษี ที่ถูก Normalize แล้ว), `shop_name` (ชื่อร้าน), `customer_name` (ชื่อลูกค้า), `status` (สถานะการดำเนินคดี), และ `remark` (หมายเหตุเพิ่มเติม)

### 3. เอนทิตี CreditRequests (ข้อมูลคำขอวงเงินเครดิต)
*   **บริบทการทำงาน:** เป็นตารางศูนย์กลาง (Core Table) สำหรับจัดการ Workflow ของระบบ ใช้เพื่อบันทึกสถานะและรายละเอียดของการร้องขอวงเงินเครดิตของลูกค้าในแต่ละครั้ง (ทั้งลูกค้าใหม่ ลูกค้าปัจจุบัน และโครงการ)
*   **โครงสร้าง (Attributes):** มี `id` เป็น Primary Key แบบ Auto Increment แต่จะใช้ `tx_id` (Transaction ID) ซึ่งกำหนดเป็นค่า UNIQUE ในฐานข้อมูล เพื่อเป็นจุดอ้างอิงหลัก (Foreign Key) ไปยังตารางลูกอื่นๆ ประกอบด้วยข้อมูลสำคัญเช่น `customer_no` (อ้างอิงลูกค้า), `status` (สถานะการอนุมัติ เช่น Draft, SalesSubmitted, Approved), `request_amount` (วงเงินที่ขอ), `request_credit_term` (เงื่อนไขวันชำระหนี้ที่ขอ) และมีฟิลด์ `snapshot_data` (TEXT/JSON) สำหรับการบันทึกภาพรวมข้อมูลทางการเงินและคะแนน (Scorecard) ไว้ ณ เวลาที่ขอเครดิต
*   **ความสัมพันธ์ (Relationship):** เป็นศูนย์กลางที่มีความสัมพันธ์แบบ One-to-Many (1:M) ไปยังเอนทิตี `CreditRequestAttachments`, `RequestComments` และ `Notifications`

### 4. เอนทิตี CreditRequestAttachments (เอกสารแนบประกอบคำขอ)
*   **บริบทการทำงาน:** ระบบเปิดให้ผู้ขอสินเชื่อแนบไฟล์ประกอบการพิจารณา (เช่น เอกสาร ภงด.50, งบการเงิน DBD) โดยไฟล์จริงจะถูกเก็บไว้ในเซิร์ฟเวอร์ และบันทึกที่อยู่ (Path) ไว้ในตารางนี้
*   **โครงสร้าง (Attributes):** อ้างอิงคำขอหลักด้วย Foreign Key `tx_id` จัดเก็บ `file_path` (ตำแหน่งไฟล์), `original_name` (ชื่อไฟล์ต้นฉบับ), `file_type` (ประเภทไฟล์), และ `uploaded_by` รวมถึงมีฟิลด์ `is_deleted` ไว้รองรับระบบ Soft Delete ในกรณีที่มีการตีกลับคำขอ (Revise) ป้องกันไม่ให้เอกสารเดิมที่ถูกลบโผล่กลับมาแสดงซ้ำ

### 5. เอนทิตี RequestComments (ความคิดเห็นและประวัติการทำงาน)
*   **บริบทการทำงาน:** ใช้สำหรับบันทึกความคิดเห็นและการลงมติ (Audit Trail) ในทุกกระบวนการของการส่งต่อคำขอ (เช่น เมื่อ Regional Manager พิจารณาส่งต่อให้ฝ่ายขาย หรือเมื่อ Finance Manager อนุมัติวงเงิน)
*   **โครงสร้าง (Attributes):** เชื่อมโยงกับคำขอด้วย `tx_id` โดยเก็บรายละเอียด `comment_text` (ข้อความหรือเหตุผล), `actor_role` (บทบาทของผู้พิจารณา), `create_by` (ผู้ใช้งานที่ดำเนินการ) และ `create_at` (เวลาที่บันทึก)

### 6. เอนทิตี Notifications (ระบบการแจ้งเตือน)
*   **บริบทการทำงาน:** รองรับระบบแจ้งเตือนภายใน (In-app Notification) เพื่ออัปเดตสถานะให้ผู้สร้างคำขอและผู้พิจารณาในลำดับถัดไปทราบ
*   **โครงสร้าง (Attributes):** เชื่อมโยงกับคำขอผ่าน `tx_id` จัดเก็บ `target_role` (กลุ่มเป้าหมาย เช่น ผู้สร้างคำขอ, ผู้จัดการฝ่ายขาย), `target_username` (เจาะจงบุคคล), `message` (ข้อความแจ้งเตือนสถานะ), `is_read` (สถานะการอ่าน) และ `create_at` (เวลาที่ระบบสร้างการแจ้งเตือน)

---

**สรุปภาพรวมทางสถาปัตยกรรม:**
การออกแบบ ER Diagram นี้ อาศัยแนวทางการแยกระหว่างข้อมูลธุรกรรมชั่วคราว (Transaction Data) และข้อมูลหลัก (Master Data) อย่างชัดเจน ฐานข้อมูลในส่วนของระบบใช้ `tx_id` เป็นตัวเชื่อมกลาง (Relation Key) เพื่อให้การจัดการเอกสาร ความเห็น และสถานะคำขอ (Workflow) มีความสมบูรณ์ ลดความซ้ำซ้อน และเอื้อให้การติดตามประวัติ (Audit Trail) เป็นไปอย่างถูกต้องตามสถาปัตยกรรมของฐานข้อมูลแบบ Relational Database (SQL)
